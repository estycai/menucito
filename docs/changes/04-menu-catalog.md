# 04 · Menu catalog: categories and products (with photos)

Status: approved
Date: 2026-10-28
Depends on: `docs/changes/02-restaurant-onboarding.md` and `docs/changes/03-logo-storage.md` (both must be done first)

## Intent
A restaurant owner loads their menu from the admin panel: creates, renames, reorders and deletes categories; creates, edits, reorders, moves and deletes products (name, description, price, availability) and gives each product one photo. Photos reuse the spec 03 pipeline (browser normalization to WebP, Worker upload to R2, public read through `/api/media/*`). This also introduces the first plan limits, with placeholder values until the business decides them.

## Scope
- In:
  - `categories` and `products` tables (one migration) with `position` ordering, `available` flag and `price_cents`.
  - API (layered): list the catalog, CRUD + reorder of categories, CRUD + reorder + move of products, upload/remove a product photo.
  - Plan limits as named placeholder constants in `packages/shared`, enforced in the service (403 `PLAN_LIMIT`).
  - Product photos: browser normalization to an 800x800 WebP, key `products/<restaurantId>/<random>.webp`, media allowlist extended to `products/`.
  - Shared helpers: ARS price parsing/formatting (cents), catalog schemas, with unit tests.
  - Admin: "Mi menú" page (`/menu`) and product editor (`/menu/products/new`, `/menu/products/:id`); link from home. Mobile-first: owners will mostly manage the catalog from a phone.
  - Small mobile pass on the pages from specs 01-03 (login, onboarding, home `/`, `/local`): check them at 375px and fix only what breaks (overflow, cramped targets). Not a redesign.
- Out: native app (the panel is a responsive web app), KV publish, "Publicar cambios" banner and the public menu page; ingredients, option groups, extras and variants (Pro, later spec); several photos per product (gallery); hiding a product or category without deleting it (only "Agotado" for now); drag-and-drop reordering; bulk import, duplicating products, AI menu from a photo; plans and payments; the panel sidebar/shell; signed/direct-to-R2 uploads; allergens, tags, stock counts.

## Spec
Scenarios (Given / When / Then):
1. Given I have a restaurant and no categories, when I open `/menu`, then I see an empty state ("Todavía no tenés categorías. Creá la primera para empezar a cargar productos.") and "Nuevo producto" is disabled.
2. Given I am on `/menu`, when I click "+ Nueva categoría" and enter "Hamburguesas", then it is created at the end of the list and selected; given an empty name or more than 40 characters, then I see a field error and the API answers 422 for the same input.
3. Given a category "Hamburguesas", when I create another one named "hamburguesas" (any casing, surrounding spaces trimmed), then the API answers 409 `CATEGORY_NAME_TAKEN` and I see "Ya tenés una categoría con ese nombre".
4. Given several categories, when I rename one or move it up/down, then the new name/order is kept after reloading `/menu`.
5. Given an empty category, when I delete it and confirm, then it disappears; given a category with products, when I delete it, then the API answers 409 `CATEGORY_NOT_EMPTY`, nothing is deleted and I see "Primero mové o eliminá los productos de esta categoría".
6. Given a category, when I click "Nuevo producto", fill name "Hamburguesa completa", description, category and price `9.000`, and click "Guardar", then the product is created at the end of that category with `priceCents = 900000`, and the list shows "$9.000" and the "Disponible" badge.
7. Given the price input, when I type `9.000`, `9000`, `9.000,50` or `$ 9.000`, then it is stored as `900000`, `900000`, `900050`, `900000` cents; given `abc`, a negative value, more than 2 decimals or more than $999.999,99, then I see a field error and the API answers 422 for an invalid `priceCents` (not an integer, negative or over `99999999`).
8. Given a product, when I edit its name, description, price or "Disponible para pedir" and click "Guardar", then the changes are kept; when I click "Cancelar", then nothing is saved and I go back to `/menu`.
9. Given a product, when I click its "Disponible"/"Agotado" badge in the list, then its availability toggles without opening the editor.
10. Given a product, when I change its category and save, then it is moved to the end of the new category.
11. Given several products in a category, when I move one up/down, then the order is kept after reloading.
12. Given a product, when I click "Eliminar producto" and confirm, then the product and its photo are removed and I go back to `/menu`.
13. Given a product (or a new one being created), when I choose a PNG/JPG/WebP/GIF in "Cambiar foto", then it is center-cropped to 800x800 ("cover"), converted to WebP and shown; for an existing product it is uploaded at once; for a new product it is uploaded right after the product is created on "Guardar".
14. Given a product with a photo, when I upload another one, then the old object is deleted from R2 and `imageUrl` points to the new one; when I click "Quitar foto", then the object and `imageUrl` are removed and the placeholder returns.
15. Given a file that is not an accepted image (including SVG) or cannot be decoded, when I select it, then I see "No pudimos leer esa imagen" and nothing is uploaded. Given an upload that is not a real WebP or is larger than 1 MB, when it reaches the API, then it answers 415 or 413 (same rules as the logo).
16. Given a restaurant on the Basic plan with `PLAN_LIMITS.basic.maxProducts` products, when I try to create one more, then the API answers 403 `PLAN_LIMIT`, "Nuevo producto" is disabled and I see "Llegaste al límite de productos del plan Básico"; editing, moving and deleting existing products still work. The header shows "N de M productos en el plan Básico" (Pro: "N productos").
17. Given a plan whose `productPhotos` is `false`, when I upload a product photo, then the API answers 403 `PLAN_LIMIT` and the photo control is replaced by the "PRO" badge (as other Pro features in the canvas); removing an existing photo still works.
18. Given two restaurants A and B, when B calls any category/product endpoint with an id that belongs to A (in the URL or as `categoryId` in the body), then the API answers 404 `CATEGORY_NOT_FOUND`/`PRODUCT_NOT_FOUND` and A's data is unchanged; `GET /api/categories` for B never includes A's data.
19. Given a reorder request whose `ids` are not exactly the current set (missing, duplicated or foreign ids), when it reaches the API, then it answers 422 and no position changes.
20. Given a product photo, when anyone requests its public URL, then it is served like a logo (`image/webp`, immutable cache, `nosniff`); given a key outside `logos/` and `products/` or a missing object, then 404.
21. Given no session, when I call any catalog endpoint, then the API answers 401; given a session without a restaurant, then 404 `RESTAURANT_NOT_FOUND`; given I open `/menu` without a restaurant, then I am redirected to `/onboarding` (existing guard).
22. Given a 375px-wide viewport on a touch device, when I create a category, create a product with a photo taken with the camera or picked from the gallery, edit its price, toggle "Agotado", move it up/down and delete it, then every step works by touch, every control is at least 44px, and the page never scrolls horizontally.

## Design
- Data (Drizzle, snake_case, `timestamp_ms` like `restaurants`), migration `0003_catalog` via `db:generate`, applied locally:
  - `categories`: `id` text PK, `restaurant_id` text NOT NULL references `restaurants.id` on delete cascade, `name` text NOT NULL, `position` integer NOT NULL, `created_at`, `updated_at`. Index `(restaurant_id, position)`. Unique expression index `(restaurant_id, lower(name))` (SQLite `lower` only folds ASCII; accented duplicates in different case are accepted, document it).
  - `products`: `id` text PK, `restaurant_id` text NOT NULL references `restaurants.id` on delete cascade, `category_id` text NOT NULL references `categories.id` on delete restrict, `name` text NOT NULL, `description` text NOT NULL default `''`, `price_cents` integer NOT NULL, `image_url` text nullable, `available` integer boolean NOT NULL default true, `position` integer NOT NULL, `created_at`, `updated_at`. Index `(restaurant_id, category_id, position)`.
  - Deviations from the vault model, to record in `Modelo-de-datos.md`: `price` -> `price_cents` (integer ARS cents: no float rounding, the WhatsApp total and future Mercado Pago amounts sum exactly); `image_url` keeps one photo per product; `description` is NOT NULL default empty.
- Delete a category with products: BLOCK with 409 `CATEGORY_NOT_EMPTY` (also enforced by `on delete restrict`). Cascade was rejected: one click would silently destroy many products and leave their R2 photos to clean up in bulk; blocking is safe, cheap and the fix is obvious to the owner (move or delete the products first).
- Mobile-first (the canvas is desktop-only at 1280px; adapt it, do not copy fixed widths): build for 360px wide first and enhance upward with Tailwind breakpoints; no horizontal page scroll at any width from 360px. Touch targets at least 44x44px (the canvas already uses 44-48px heights). Forms are a single column on mobile (the editor's "Categoría"/"Precio" pair and the two-column editor stack). On `/menu` below `md`: the categories aside becomes a row of category chips above the product list (the chip row may scroll horizontally inside itself; the page does not), the "Nuevo producto" button stays reachable at the bottom of the screen (sticky), product rows keep thumbnail, name, price and badge with the name truncated, and row actions (up/down, availability) sit on the right where a thumb reaches them. The editor footer ("Eliminar producto", "Cancelar", "Guardar") stacks with "Guardar" full width. Use `inputMode="decimal"` on the price input.
- Reordering on touch: up/down buttons ("Subir"/"Bajar") on every category and product, not drag-and-drop. Drag-and-drop on touch fights with page scrolling, needs a long-press library, is hard to hit one-handed on a long list and is not accessible to keyboard and screen-reader users; buttons work identically with mouse, touch and keyboard and add no dependency. Each tap sends the full new order (`PUT .../order`) with an optimistic update; disable the first item's "Subir" and the last item's "Bajar". Drag-and-drop stays out of scope (could be added later on desktop only).
- Ordering: `position` is a 0-based integer per restaurant (categories) and per category (products); lists sort by `position`, then `created_at`. New items and moved products get `max(position) + 1` of the target. Reorder endpoints receive the full ordered id list and rewrite `0..n-1` in one D1 batch (atomic); gaps after deletes are fine.
- Availability: `available = false` means "Agotado" (shown in the public menu later, not orderable). No hidden state in this change.
- Endpoints (all behind `requireSession`, JSON errors `{error: {code, message}}`; new routers `routes/categories.ts` at `/api/categories` and `routes/products.ts` at `/api/products`, do NOT mount them under `/api` with a `use("*")`, it would put a session on `/api/media`):
  - `GET /api/categories` -> 200 `{categories: [{id, name, position, products: [Product]}], usage: {products, maxProducts: number | null, productPhotos: boolean}}` (one query per table, grouped in the service).
  - `POST /api/categories` `{name}` -> 201 category; `PATCH /api/categories/:id` `{name}` -> 200; `DELETE /api/categories/:id` -> 204 / 409 `CATEGORY_NOT_EMPTY`; `PUT /api/categories/order` `{ids}` -> 204; `PUT /api/categories/:id/products/order` `{ids}` -> 204.
  - `POST /api/products` `{categoryId, name, description, priceCents, available}` -> 201 / 403 `PLAN_LIMIT`; `GET /api/products/:id` -> 200; `PATCH /api/products/:id` (partial, same fields) -> 200; `DELETE /api/products/:id` -> 204.
  - `PUT /api/products/:id/photo` (multipart, field `file`) -> 200 `{imageUrl}` / 403 / 413 / 415; `DELETE /api/products/:id/photo` -> 204 (also when there is none).
  - Product shape: `{id, categoryId, name, description, priceCents, imageUrl, available, position, createdAt, updatedAt}`.
  - Errors: 401, 403 `PLAN_LIMIT`, 404 `RESTAURANT_NOT_FOUND`/`CATEGORY_NOT_FOUND`/`PRODUCT_NOT_FOUND`, 409 `CATEGORY_NAME_TAKEN`/`CATEGORY_NOT_EMPTY`, 413 `FILE_TOO_LARGE`, 415 `UNSUPPORTED_MEDIA_TYPE`, 422 `VALIDATION_ERROR`.
- Tenant scoping: services call `restaurantOf(userId)` first, then pass `restaurant.id` to every repository call; repositories filter `where restaurant_id = ? and id = ?` (never by id alone). A foreign or unknown id is indistinguishable: 404, never 403. A `categoryId` in the body is checked the same way.
- Layers (new files): `repositories/categories.ts`, `repositories/products.ts`, `services/catalog.ts` (`catalogServiceFor(db, bucket)`; categories, products, plan checks, photos). Generalize `UniqueViolationError` into `repositories/errors.ts` (table + column or index name; parse both `UNIQUE constraint failed: <table>.<column>` and `UNIQUE constraint failed: index '<name>'`, which is what SQLite reports for expression indexes), keeping restaurants behavior and tests unchanged. Extract the shared upload validation from `services/logos.ts` (`hasWebpSignature`, size and content type) into one helper with generic `FileTooLargeError`/`UnsupportedMediaTypeError` (same codes); the logo endpoints must behave exactly as before. The route `errorResponse`/`statusFor` mapping is shared, not copied.
- Plan limits (`packages/shared/src/plans.ts`): `PLAN_LIMITS = { basic: { maxProducts: 40, productPhotos: true }, pro: { maxProducts: null, productPhotos: true } }` and `planLimitsFor(plan: string)` (unknown values -> `basic`, the most restrictive). Every value carries a `// PLACEHOLDER: pending business decision (see docs/changes/04-menu-catalog.md, Open questions)` comment; 40 and photos-on-Basic come from the proposal in `Planes-y-precios.md` ("Hasta ~40 productos, 1 foto por producto") and the canvas, they are NOT final. The service checks `count(products) >= maxProducts` before insert (403 `PLAN_LIMIT`) and `productPhotos` before a photo upload. Only creation is limited: a restaurant above the limit (e.g. after a downgrade) keeps, edits and deletes its products. Known gap: two concurrent creates can exceed the limit by one (count then insert); acceptable, document it in a comment. Tests read the constant, never a hard-coded 40.
- Product photos: key `products/<restaurantId>/<random>.webp`, `image_url` stores the public path (`/api/media/products/...`), key derived with `keyFromPublicPath`. Same rules as the logo: <= 1 MB (`PRODUCT_PHOTO_MAX_BYTES`), `Content-Type: image/webp`, `RIFF....WEBP` signature; replace order: write new object, update DB (scoped by restaurant and product), then delete the old one (failure logged, not raised); if the DB update fails, delete the new object. Product delete: delete the row, then the photo quietly. Upload path stays Worker -> R2 (not signed URLs) for the reason in spec 03 (S3 credentials, local emulator); an 800x800 WebP is ~50-150 KB. Record this in `Storage-e-imagenes.md`, closing the "fotos de productos, a definir" line.
- Media: extend the allowlist in `services/media.ts` to `^(logos|products)\/[A-Za-z0-9-]+\/[A-Za-z0-9-]+\.webp$`; rename `LOGO_CONTENT_TYPE` usages there to a neutral `MEDIA_CONTENT_TYPE` (`image/webp`). Nothing else in the media route changes.
- Browser normalization (`apps/admin/src/lib/image.ts`): generalize into `normalizeImage(file, {size, fit: "contain" | "cover", sourceTypes, maxBytes})`; `normalizeLogo` keeps its exact behavior (512, contain, transparent, SVG allowed). Add `normalizeProductPhoto`: 800x800, "cover" (scale to fill and center-crop) with a new pure `coverRect`, qualities `[0.82, 0.7, 0.6]`, accepts `image/png, image/jpeg, image/webp, image/gif` (no SVG: photos are not vector art and it keeps the attack surface smaller). Why 800 cover: every product slot in the canvas is square (56 px list, 88 px public card, 96 px editor) or a full-width banner (390 px public detail); 800 covers 390 CSS px at 2x DPR, and cover avoids letterboxing real photos. The photo file input uses `accept="image/*"` with NO `capture` attribute, so phones offer both the camera and the gallery; the real type check happens in `normalizeProductPhoto` (anything outside the accepted list, e.g. HEIC where the browser does not convert it to JPEG, shows "No pudimos leer esa imagen"). Phone camera photos are large (12+ MP): decode with `createImageBitmap` and release the bitmap right after drawing to keep memory low.
- Shared (`packages/shared/src/catalog.ts`): `categoryNameSchema` (trimmed, 1-40), `createProductSchema`/`updateProductSchema` (name 1-80 trimmed, description 0-300 trimmed, `priceCents` int 0..99_999_999, `available` boolean, `categoryId` string), `reorderSchema` (`ids`: non-empty unique strings), `parseArsPrice(input): number | null` (strips `$` and spaces, `.` thousands, `,` up to 2 decimals) and `formatArs(cents)` ("$9.000", "$9.000,50"), exported from `index.ts`, with Vitest tests.
- Admin: `lib/catalog.ts` (query key `["catalog", userId]`, hooks for every endpoint, mutations invalidate the catalog query), `pages/MenuPage.tsx` (`/menu`), `pages/ProductEditorPage.tsx` (`/menu/products/new?category=<id>` and `/menu/products/:id`), `components/ProductPhotoUploader.tsx` (96 px square preview, "Cambiar foto", "Quitar foto", hint "Se comprime sola antes de subir.", loading/error states; same structure as `LogoUploader`), routes behind `RequireAuth` + `RequireRestaurant`, link "Mi menú" on `WelcomePage`. Category controls (not in the canvas, keep them small): on the selected category header "Renombrar" (inline input), "Eliminar", and up/down icon buttons with `aria-label` "Subir"/"Bajar"; same up/down buttons on each product row; the status badge is a button toggling availability. Deletes ask with `window.confirm` ("¿Eliminar «<nombre>»? No se puede deshacer."). Price input shows and accepts the AR format, converted with the shared helpers. 404 on a product id in the editor -> back to `/menu`.
